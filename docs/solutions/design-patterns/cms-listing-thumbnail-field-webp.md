# Dedicated WebP thumbnail field for CMS listing tiles

## Problem

CMS images imported through the Data API never get `srcset` variants (see [webflow-cms-image-emission.md](../conventions/webflow-cms-image-emission.md)). A listing grid bound to each item's hero image therefore downloads and decodes the full 2560 to 4000px original (1 to 4MB) for a tile that renders at about 620px. On one project the listing page transferred over 50MB, and when a Finsweet filter re-added tiles, each re-decode took up to half a second, showing blank tiles (see [finsweet-cmsfilter-double-flash-back-to-all.md](../integration-issues/finsweet-cmsfilter-double-flash-back-to-all.md)).

## Pattern

Add a separate `Thumbnail` Image field to the collection, fill it by script with a resized WebP of the hero, and bind the listing tile to it. The hero field is never written, so its file (and any variants it has) stay untouched.

Script outline (`scripts/api/webflow/create-<collection>-thumbnails.mjs`, two commands, dry run unless `--apply`):

1. **`create-field`:** `POST /v2/collections/{id}/fields` with `{ type: 'Image', displayName: 'Thumbnail', helpText: 'Generated by script; replace with a 1600px wide image if the hero changes.' }`. Check the field count first (60-field cap; see [webflow-cms-field-limit-migration.md](../workflow-issues/webflow-cms-field-limit-migration.md)).
2. **`run`:** for each item with a hero image and no thumbnail:
   - download the hero, then `sharp(original).rotate().resize({ width: 1600, withoutEnlargement: true }).webp({ quality: 80 })`
   - upload to the asset library through the presigned flow (`POST /v2/sites/{siteId}/assets` with `fileName` and MD5 `fileHash`, then POST the form to `uploadUrl`); skip the upload when an asset with the same file name already exists
   - `PATCH /v2/collections/{id}/items/{itemId}` with `{ fieldData: { thumbnail: { fileId, url: hostedUrl, alt: hero.alt || name } } }`
   - write a log (item, status, KB saved) and support `--item <slug>` for a one-item probe
3. Writes go to staged data only; publish separately after checking one item live.

Sizing: 1600px wide covers a roughly 620px tile on 2x screens. Results were about 100 to 290KB per tile instead of 1 to 4MB.

Then in the Designer, rebind the tile image on the listing page (and any other card that shows the hero) to `Thumbnail`.

## Why This Works

The thumbnail is still an API import with no `srcset`, but one fixed size chosen for the tile is close to what a `srcset` would have picked, and WebP at quality 80 is a fraction of the original's weight. Decode time drops with it, so filtered tiles paint within a single fade-in.

## Gotchas

- New CMS items need a thumbnail too. Re-run the script, or tell the editor to upload a 1600px image into the field (an Editor upload also gets real `srcset` variants).
- Copy the hero's alt into the thumbnail at write time; the field has its own alt.
- Do not overwrite existing thumbnails on reruns unless targeting one item explicitly.
- The presigned-upload response returns `id` and `hostedUrl` at the top level in some API versions and under `.asset` in others; read both.
